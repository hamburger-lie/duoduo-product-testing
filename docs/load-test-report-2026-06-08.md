# Soul Unified API 压测与优化报告

日期：2026-06-08  
环境：本地 Docker 模拟 2 核 2G 线上资源  
测试工具：Locust，预生成 JWT token 池，绕过登录限流  
测试入口：`tests/performance/locustfile_tokens.py`

## 1. 结论摘要

本轮优化后，系统在模拟 2 核 2G 资源下的接口承载能力有明显提升。

- 100 并发：0 失败，P95 130ms，P99 290ms，体验较稳。
- 150 并发：0 失败，P95 430ms，P99 740ms，可作为当前较稳的目标承载档。
- 200 并发：失败 2 次，P95 1200ms，P99 1800ms，没有雪崩，但尾延迟明显升高，属于高压区。

本次压测覆盖了认证后的混合 API 流量，以及部分评测创建和运行流程，但不是“每个用户完整跑完产品创建、问卷生成、评测执行、报告生成并拿到最终报告”的端到端闭环测试。

当前可以得出的判断：

- 接口层、认证缓存、热点列表缓存、activity 日志关闭/异步、评测 run 任务化排队后，150 并发以内体验明显改善。
- 200 并发下系统没有出现之前的大面积 500/503，但响应尾部会变长。
- 报告生成任务化尚未纳入本阶段，完整报告链路还需要第二阶段单独测试和优化。

## 2. 测试范围

本次使用的 Locust 脚本是认证后混合流量测试，主要任务包括：

| 类型 | 接口 | 说明 |
|---|---|---|
| 高频读 | `GET /api/v1/personas` | 权重最高，模拟用户频繁查看人群画像 |
| 高频读 | `GET /api/v1/products` | 产品列表 |
| 高频读 | `GET /api/v1/credits/balance` | 积分余额 |
| 高频读 | `GET /api/v1/evaluations` | 评测列表 |
| 高频读 | `GET /api/v1/history` | 历史记录 |
| 健康检查 | `GET /health/live` | 不碰数据库，用于观察 API 本体是否存活 |
| 写入 | `POST /api/v1/products` | 创建产品 |
| 部分流程 | 创建 evaluation -> 选择 persona -> 生成 survey -> run evaluation | 覆盖评测入口流程 |
| 报告查询 | `GET /api/v1/reports/by-evaluation/{id}` | 报告未生成时 400/404 被视为正常 |

不包含的内容：

- 不包含登录接口压测，登录已通过预生成 JWT token 绕过。
- 不保证 100/150/200 个用户同时都在生成问卷。
- 不等待 worker 完成所有评测任务。
- 不验证最终报告一定生成成功。
- 不统计端到端报告完成耗时。

因此，本报告主要反映：

> 认证后 API 混合流量 + 评测 run 排队入口的承载能力。

完整全流程能力仍需专项测试：

```text
创建产品
-> 创建评测
-> 选择 persona
-> 生成问卷
-> run evaluation
-> 等待 worker 执行完成
-> 查询报告
-> 报告生成成功
```

## 4. 修改前问题

最早的 200 并发压测暴露出明显瓶颈：

| 指标 | 修改前结果 |
|---|---:|
| 总请求 | 1655 |
| 失败率 | 41.5% |
| 主要失败 | 数据库连接等待超时后返回 500 |
| 碰库接口 P50 | 约 30 秒 |
| `/health/live` | 0 失败，约 7ms |
| API CPU | 接近 0 |
| Postgres 连接数 | 约 31 |

根因判断：

```text
DB 连接池 = pool_size 10 + max_overflow 20 = 最多 30 个连接
200 并发大量请求同时碰库
多数请求排队等待连接
等待超过 pool_timeout
接口超时或返回 500
```

当时 `/health/live` 正常，API CPU 也不高，说明不是 API 进程崩溃，也不是 CPU 算力先到顶，而是请求阻塞在数据库连接池和数据库访问链路上。

## 5. 第一轮优化内容

### 5.1 数据库连接池与快速失败

修改内容：

- 增加 `DB_POOL_TIMEOUT` 配置。
- 提高本地压测环境 DB pool 容量。
- 将数据库连接池超时转换成明确的 503。

目的：

- 避免请求卡满 30 秒后才失败。
- 在系统高压时快速降级，而不是拖死用户请求。

### 5.2 热点列表缓存

修改内容：

- `GET /api/v1/personas` 增加 Redis 缓存。
- `GET /api/v1/products` 增加 Redis 缓存。
- 对 create/update/delete 等写入操作做缓存失效。

目的：

- 减少高频只读接口对数据库的压力。
- 降低 P95/P99 尾延迟。

### 5.3 activity 日志优化

修改内容：

- 增加 `ACTIVITY_LOG_ENABLED`。
- 增加 `ACTIVITY_LOG_SAMPLE_RATE`。
- 增加 `ACTIVITY_LOG_ASYNC`。
- 压测环境关闭 activity 日志写入。
- 生产环境可配置采样，例如 10%。

目的：

- 避免每个认证请求都额外写一条用户行为日志。
- 降低数据库写入压力。
- 避免日志写入影响主请求响应。

### 5.4 current_user 用户缓存

修改内容：

- 对安全读请求 `GET/HEAD/OPTIONS` 增加 current user Redis 缓存。
- 缓存 TTL 默认 300 秒。
- `POST/PUT/PATCH/DELETE` 等写请求绕过用户缓存。
- 用户资料更新、头像更新后主动失效用户缓存。

目的：

- 避免每个认证请求都查一次 users 表。
- 对高并发读流量减少数据库压力。
- 写请求保持数据一致性优先。

### 5.5 run evaluation 任务化排队

修改内容：

- `run evaluation` 改为进入 Celery 队列。
- API 立即返回 `202 Accepted`。
- evaluation 状态先进入 `queued`。
- worker 真正开始处理时再进入 `answering`。

目的：

- 避免用户请求同步等待评测执行。
- 在高并发 run 时通过队列削峰。
- 让 API 层保持响应能力。

说明：

- 本阶段尚未处理报告生成任务化。
- 报告生成属于第二阶段优化范围。

## 6. 修改后测试结果

### 6.1 本轮最终结果

| 并发 | 总请求 | 失败 | RPS | P50 | P95 | P99 | 最大延迟 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 100 | 9600 | 0 | 53.5 | 18ms | 130ms | 290ms | 960ms |
| 150 | 13880 | 0 | 77.3 | 66ms | 430ms | 740ms | 1900ms |
| 200 | 15280 | 2 | 85.2 | 380ms | 1200ms | 1800ms | 3200ms |

200 并发的 2 个失败为：

```text
ConnectionResetError(104, 'Connection reset by peer')
```

不是业务 500，也不是数据库 pool timeout。

### 6.2 修改前后对比

#### 200 并发最早问题版本 vs 当前版本

| 指标 | 修改前 | 当前 |
|---|---:|---:|
| 总请求 | 1655 | 15280 |
| 失败 | 约 41.5% | 2 次 |
| P95 | 约 30 秒级 | 1200ms |

| 最大延迟 | 约 60 秒 | 3200ms |
| 主要失败 | DB pool timeout / 500 | 偶发连接 reset |
| 系统状态 | 碰库接口大面积阻塞 | 高压但未雪崩 |

#### 缓存优化后、activity/current_user/run 排队前 vs 当前

| 并发 | 阶段 | 总请求 | 失败 | RPS | P95 | P99 | 最大延迟 |
|---:|---|---:|---:|---:|---:|---:|---:|
| 100 | 中间版本 | 9276 | 0 | 51.7 | 260ms | 1400ms | 3300ms |

- 200 并发 P99 从 5600ms 降到 1800ms。

## 7. 当前容量判断

### 7.1 150 并发以内

当前版本在 150 并发下：

- 0 失败。
- P95 430ms。
- P99 740ms。
- 最大延迟 1900ms。

判断：

> 150 并发以内可以作为当前较稳的目标承载区间。

对于真实线上场景，如果“200 人同时”指的是 200 个在线用户，其中只有一部分人在频繁操作，那么当前配置有较大概率可以稳定运行。

### 7.2 200 并发

当前版本在 200 并发下：

- 失败 2 次。
- P95 1200ms。
- P99 1800ms。
- 最大延迟 3200ms。

判断：

> 200 并发已经进入高压区，但不再雪崩。

它说明系统具备一定的 200 并发抗压能力，但用户体验会出现明显尾延迟。若业务要求 200 人同时高频操作也保持“无感”，还需要继续优化和增加排队/限流保护。

### 7.3 生成问卷能力判断

本次压测包含 `POST /api/v1/surveys/generate`，但它不是 100/150/200 个用户同时都在生成问卷。

因此可以说：

> 100/150 并发混合流量下，问卷生成夹在整体流程中没有拖垮系统。

但不能说：

> 100 人同一秒同时生成问卷也完全无感。

要确认这个点，需要单独做“问卷生成专项压测”：

```text
100 个用户
每个用户创建产品
创建评测
选择 persona
同时请求生成问卷
统计 /api/v1/surveys/generate 的 P95/P99/失败率
```

## 8. 剩余风险

### 8.1 报告生成还未任务化

报告生成当前不在第一阶段优化范围内，也没有进入完整闭环压测。

风险：

- 如果报告生成仍然是同步或重计算型逻辑，未来可能成为新的瓶颈。
- 用户大量同时查看/生成报告时，可能再次拉高 P95/P99。

建议：

- 第二阶段将报告生成也纳入 Celery 任务。
- API 返回报告生成状态。
- 前端轮询或 WebSocket 获取结果。
- 报告结果缓存，避免重复生成。

### 8.2 200 并发下尾延迟仍明显

200 并发 P95/P99 虽然大幅下降，但仍到达 1.2s/1.8s。

风险：

- 高峰期用户会感觉部分操作变慢。
- 如果真实线上还有外部 AI API 调用、网络延迟、真实图片处理，尾延迟可能更高。

### 8.3 当前不是完整端到端测试

当前测试更偏 API 混合流量，不代表完整业务闭环。

风险：

- worker 队列积压时间没有被统计。
- 评测完成时间没有被统计。
- 报告最终可见时间没有被统计。

## 9. 优化建议

### 9.1 短期必须做

1. 保持 activity 日志可配置关闭/采样/异步。
2. 保持 current_user 缓存。
3. 保持 personas/products 热点列表缓存。
4. 保持 evaluation run 队列化。
5. 对 200 并发增加保护策略：
   - 队列长度限制。
   - 超过阈值返回“排队中/稍后重试”。
   - 不让请求无限挤进数据库。

### 9.2 第二阶段建议

1. 报告生成任务化。
2. 报告查询缓存。
3. 增加任务状态接口：

```text
queued
answering
generating_report
completed
failed
```

4. 前端展示排队状态和预计等待时间。
5. 对高成本接口增加用户级并发限制，例如同一用户同时只能运行 1 个评测任务。

### 9.3 专项压测建议

建议补充 3 类专项压测：

#### A. 问卷生成专项

目标：

```text
确认 30 / 50 / 100 人同时生成问卷时的 P95/P99 和失败率。
```

指标：

- `/api/v1/surveys/generate` P95/P99。
- 失败率。
- 数据库连接数。
- worker 是否受影响。

#### B. 完整评测闭环专项

目标：

```text
确认用户从创建产品到报告可见的端到端耗时。
```

指标：

- API 提交耗时。
- 队列等待耗时。
- worker 执行耗时。
- 报告生成耗时。
- 总完成耗时。

#### C. 200 并发保护专项

目标：

```text
验证超过承载阈值后，系统是排队/降级，而不是失败/雪崩。
```

指标：

- 503/429 数量。
- 队列长度。
- 用户可感知等待时间。
- API 是否保持健康。

## 10. 推荐上线策略

当前建议：

- 以 150 并发以内作为当前稳定体验目标。
- 200 并发作为可承受但需保护的高压目标。
- 不建议承诺“200 人同时高频完整生成评测报告也无感”。

建议对外表述：

> 当前版本已完成 API 层和评测提交链路的第一阶段性能优化。在模拟 2 核 2G 环境下，150 并发以内 0 失败，P99 小于 1 秒；200 并发下系统不再雪崩，失败率极低，但尾延迟上升，后续将通过报告任务化和队列保护继续优化完整评测闭环体验。
