> 计划书 / Design Spec
> 创建日期：2026-05-09
> 最后更新：2026-05-09（v5 · 小样策略：前端先行 + Mock 后端 + 迁移友好）

## 1. 项目概述

### 1.1 一句话定位
用户上传产品图 + 写一段描述，**3 位虚拟消费者**会按预设话题逐条给出真实反馈（思考过程 + 口头回答），结束后自动出一份调研报告。

### 1.2 给用户的体验
- 简单：**只两步**——上传图 + 写描述 → 开始调研
- 真实：每位角色有独立人设，思考与说话双流可见
- 可干预：可以随时**引用某条回复**追问该角色
- 不打扰：报告等对话**自然结束**后才出现，不打断节奏

### 1.3 核心机制（仅团队内部理解）
- 后台基于"灵魂附着"机制，根据图片+描述自动生成 3 份不同 Persona Prompt
- 模型层针对**美妆 + 护肤**品类调优（前端不暴露品类选择）
- "角色持续输出大量内容"是**有意设计**：让用户在等待报告期间不空等，而是看到丰富反馈
- 报告基于完整对话内容综合生成

## 2. 目标用户与核心场景

### 2.1 目标用户
不限。任何人都可使用——品牌方、调研员、内容创作者、学生、好奇的普通人都可以。

### 2.2 核心场景
**「上传产品 → 看 3 位消费者按话题反馈 → 拿到调研报告」**

具体使用：
- 测试一款新品的第一印象（包装、定位、视觉）
- 看不同画像消费者关注点的差异
- 模拟不同消费者使用产品的反应
- 探索市场反馈方向

---

## 3. 端到端流程

```
[1] 上传产品图 + 写描述（≥20 字）→ 点「开始调研」
       ↓
[2] 短暂加载 → 3 位虚拟消费者依次登场（头像 + 姓名 + 职业）
       ↓
[3] 系统按预设话题循环驱动 →
       角色 1 → 角色 2 → 角色 3 各自给出【💭 思考】+【🗨 回答】
       （用户可中途【引用】某条回复追问该角色）
       ↓
[4] 全部预设话题走完 → 对话自然结束
       ↓
[5] 系统输出调研报告（在对话页底部直接出现）
       ↓
[6] 自动保存到「我的调研历史」
```

## 4. 输入设计

### 4.1 输入约束
| 项 | 约束 |
|---|---|
| 产品图 | 1-3 张产品图 / 品牌图，至少 1 张 |
| 不接受 | 人物自拍、生活场景、风景等无关图（系统自动检测，不符合给提示） |
| 文字描述 | **≥20 字**，引导：「这是一款 \_\_\_，主打 \_\_\_，希望了解 \_\_\_」 |
| 品类 | 用户**无需选择**。系统按美妆/护肤场景调优 |

### 4.2 模型层（候选）
- **识图**：豆包视觉模型（优先候选）
- **对话**：豆包对话模型（待 Phase 2 选型敲定）

## 5. 角色生成（后端机制 · 用户不可见）

### 5.1 后端做什么
1. 接收图片 + 文字描述
2. 视觉模型解析产品图 → 提取产品/品牌特征
3. 生成 3 份 **不同画像的完整 System Prompt**（不同年龄/消费力/与品类关系/性格）
4. 注入预设话题列表 + 双流输出格式
5. 启动多角色对话编排

### 5.2 用户看到什么
- 短暂加载动效 → 3 张角色卡依次显形
- **每张卡只显示**：头像 + 姓名 + **职业**（按你确认）
- **不展示** Prompt 原文、年龄区间、消费态度等内部字段

### 5.3 预设话题列表（驱动方式 = A 方案）
系统**按固定顺序循环**触发以下话题，每个话题让 3 位角色依次回答：

```
1. 第一印象（看到这款产品的瞬间感受）
2. 视觉与包装评价
3. 品牌联想与档次感
4. 价格预期
5. 购买意愿与犹豫点
6. 适合什么人 / 不适合什么人
7. 与同类产品比较
8. 担心 / 疑问点
9. 改进建议
```

> 话题数量、顺序可在实施时调参；总轮数控制在 **8-10 轮**，让对话有充分内容但不过长。

### 5.4 用户可以做什么
- **静默观看**：不干预，等系统跑完 → 出报告
- **引用追问**：长按或点击某条回复 → "引用并追问" → 该角色单独回应一轮
- **结束**：随时点"结束调研"提前终止 → 仍生成报告

## 6. 三角色并行对话界面（核心页面）

### 6.1 角色身份标识（已简化 · 按你确认）
每条发言带：
- 角色头像
- 姓名
- **职业**（如"白领" / "大学生" / "全职妈妈" / "护士"）

不显示年龄、城市、标签等。

### 6.2 双流输出（不变）
| 流 | 视觉 | 内容 |
|---|---|---|
| **思考流** | 灰色斜体 / 半透明 / 💭 图标 | 没说出口的真实想法、犹豫、偏见 |
| **说话流** | 标准聊天气泡 + 角色头像 | 实际说出的话 |

### 6.3 视觉示意（B 方案 · 单列依次出现）

```
┌──────────────────────────────────┐
│ 💬 系统话题：你看到这款产品的第一印象？│
└──────────────────────────────────┘

  🟣 [头像] 小芸 · 白领
  ╭ 💭 ─────────────────────────╮
  │ 这包装有点像 SK-II...贵的吧？ │
  ╰────────────────────────────╯
  ╭ 🗨 ────────────────────────╮
  │ 包装挺有质感的，应该不便宜吧？ │
  ╰────────────────────────────╯
   ↓
  🟢 [头像] 王姐 · 全职妈妈
  ╭ 💭 ─────────────────────────╮
  │ 又是网红包装...用的人多吗？   │
  ╰────────────────────────────╯
  ╭ 🗨 ────────────────────────╮
  │ 长得是挺好看，但我更看成分。   │
  ╰────────────────────────────╯
   ↓
  🟡 [头像] 朵朵 · 大学生
  ╭ 💭 ─────────────────────────╮
  │ 好可爱！想要！...买不起呜    │
  ╰────────────────────────────╯
  ╭ 🗨 ────────────────────────╮
  │ 也太好看了吧！是不是限定款？   │
  ╰────────────────────────────╯

  [💬 系统下一话题：视觉与包装评价 ...]
```

### 6.4 引用追问交互
- 长按 / 点击任一角色的【🗨 回答】气泡 → 弹出操作 "引用并追问"
- 弹出小输入框：用户输入追问内容
- 仅被引用的那位角色回应（同样 💭 + 🗨 双流）
- 追问结束后系统继续走原话题序列

### 6.5 报告呈现（重要：不打断节奏）
- 系统话题全部走完 → 显示「调研已完成 ·  正在整理报告」过渡条
- 报告就地生成 → 在对话流末尾以**报告卡片**形式出现
- 卡片可展开 / 收起 / 复制 / 导出
- 整段对话 + 报告**自动归档**到历史档案

### 6.6 报告内容（建议结构）
1. 产品概况（系统对产品的理解摘要）
2. 3 位角色画像简表
3. 关键反馈共性（多人都提到的）
4. 关键反馈差异（人群间观点分歧）
5. 主要顾虑 / 改进建议
6. 推荐目标人群

## 7. 微信小程序界面结构

### 7.1 页面（精简至 5 页）
| # | 页面 | 核心元素 |
|---|---|---|
| P0 | **首页** | 我的调研历史列表 + 「+ 新调研」按钮 + 底部 Tab |
| P1 | **新建调研** | 上传产品图（1-3 张）+ 描述输入框（≥20 字）+ 「开始调研」按钮 |

### 7.2 微信小程序设计语言
- 主色：克制（灰白基调 + 一种主题色，建议雾紫 / 灰青）
- 字体：PingFang / 系统默认
- 圆角：12-16px，气泡 18px
- 底部 Tab：调研 / 我的
- 顶部胶囊按钮（小程序原生）保留

### 7.3 Phase 1 出稿范围
**4 张关键页面**：P1（新建）、P2（角色登场）、P3（对话+报告）、P4（历史）

## 8. 外部接口规范（系统边界）

### 8.1 系统职责划分

```
┌─────────────────────────┐
│   [输入流程程序]          │  外部 — 由其他程序负责
│   图片上传 / 校验 / 预处理 │
└────────────┬────────────┘
             │ 接口 ①「调研输入接口」
             ↓
┌─────────────────────────┐
│   角色引擎 + 小程序       │  本项目核心（你负责）
│   - Persona 生成         │
│   - 多角色对话编排       │
│   - 小程序前端          │
└────────────┬────────────┘
             │ 接口 ②「对话→报告 接口」
             ↓
┌─────────────────────────┐
│   [报告生成程序]          │  外部 — 由其他程序负责
│   消费对话 → 输出报告     │
└─────────────────────────┘
                          │ 报告回写接口
                          ↓
                     小程序展示
```

### 8.2 接口 ①「调研输入接口」InputAPI

**方向**：[输入流程程序] → [角色引擎]
**触发时机**：用户上传图片+描述并校验通过后，输入程序主动调用启动调研。
**协议**：HTTP POST + JSON

**请求**
```http
POST /api/v1/research/sessions
Content-Type: application/json

{
  "userId": "string",
  "images": [
    {
      "url": "string",            // 已上传到对象存储的可访问 URL
      "mimeType": "image/jpeg",
      "size": 12345
    }
  ],
  "description": "string",         // 文字描述，长度 ≥ 20
  "createdAt": "2026-05-09T12:34:56Z"
}
```

约束：`images` 长度 1-3，`description` 长度 ≥ 20。

**响应（成功）**
```json
{
  "sessionId": "string",           // 会话唯一 ID（后续接口都用这个）
  "status": "started",
  "personas": [
    {
      "personaId": "p1",
      "name": "小芸",
      "occupation": "白领",
      "avatarUrl": "string"
    },
    { "personaId": "p2", "name": "王姐", "occupation": "全职妈妈", "avatarUrl": "string" },
    { "personaId": "p3", "name": "朵朵", "occupation": "大学生", "avatarUrl": "string" }
  ],
  "topics": ["第一印象", "视觉与包装评价", "..."]
}
```

**响应（失败）**
```json
{
  "status": "rejected",
  "errorCode": "INVALID_IMAGE | DESCRIPTION_TOO_SHORT | NOT_PRODUCT_IMAGE | QUOTA_EXCEEDED",
  "errorMessage": "string"
}
```

### 8.3 接口 ②「对话→报告 接口」DialogueAPI

**方向**：[角色引擎] → [报告生成程序]
**两种推荐模式**，外部报告程序可任选其一或组合使用：

#### 模式 A · 实时事件推送（推荐 · Webhook）

角色引擎每产生一条新内容就 POST 给报告程序的回调地址：

```http
POST {report_callback_url}
Content-Type: application/json

{
  "sessionId": "string",
  "sequence": 12,                  // 自增序号，可用于排序去重
  "eventType": "topic_started" | "persona_response" | "user_followup" | "dialogue_completed",
  "timestamp": "ISO8601",
  "payload": { ... }               // 详见下方
}
```

**事件类型与 payload**：

| eventType | payload |
|---|---|
| `topic_started` | `{ "topicIndex": 1, "topicName": "第一印象" }` |
| `persona_response` | `{ "personaId": "p1", "topicIndex": 1, "thinking": "...", "speech": "..." }` |
| `user_followup` | `{ "quotedMessageId": "...", "targetPersonaId": "p2", "userQuestion": "...", "thinking": "...", "speech": "..." }` |
| `dialogue_completed` | `{ "totalRounds": 9, "completedAt": "ISO8601" }` |

#### 模式 B · 终态全量拉取（备选）

报告程序在收到 `dialogue_completed` 后（或自行轮询）拉取完整对话：

```http
GET /api/v1/research/sessions/{sessionId}/transcript

Response:
{
  "sessionId": "string",
  "status": "completed | in_progress | terminated",
  "personas": [...],               // 同接口 ① 返回
  "topics": [...],
  "messages": [
    {
      "messageId": "string",
      "type": "topic | response | followup",
      "topicIndex": 1,
      "personaId": "p1",
      "thinking": "string",
      "speech": "string",
      "timestamp": "ISO8601"
    }
  ],
  "metadata": {
    "originalImages": [...],
    "originalDescription": "...",
    "totalRounds": 9,
    "duration": "PT5M30S"
  }
}
```

#### 报告回写接口（报告程序 → 角色引擎）

报告生成完后，由报告程序调用此接口把报告交还，小程序立即在对话页底部呈现报告卡片：

```http
POST /api/v1/research/sessions/{sessionId}/report
Content-Type: application/json

{
  "format": "markdown | structured",
  "content": "string",              // format=markdown 时使用
  "sections": [                     // format=structured 时使用
    { "title": "产品概况",  "content": "..." },
    { "title": "三位画像",  "content": "..." },
    { "title": "共性反馈",  "content": "..." },
    { "title": "差异反馈",  "content": "..." },
    { "title": "改进建议",  "content": "..." },
    { "title": "目标人群",  "content": "..." }
  ],
  "generatedAt": "ISO8601"
}

Response: { "status": "received" }
```

### 8.4 共用数据模型

| 实体 | 字段 |
|---|---|
| `Session` | sessionId / userId / createdAt / status |
| `Persona`（前端可见） | personaId / name / occupation / avatarUrl |
| `Persona`（内部完整） | 上述 + Persona Core 8 字段 + Persona Depth 6 字段（**不外传**） |
| `Message` | messageId / type / topicIndex / personaId / thinking / speech / timestamp |

### 8.5 鉴权与可靠性
- 接口间使用 API Key（请求头 `X-API-Key`）+ sessionId 双重校验
- Webhook 推送应支持失败重试（指数退避，最多 5 次）
- 具体鉴权实现 Phase 2 实施时确定

## 9. 小样实施策略（v5 新增）

### 9.1 当前选择
**当前 v4/v5 规格 = 小样（MVP 原型）**。
按以下策略推进，优先把前端跑起来，后端解耦延后接入。

### 9.2 阶段顺序
```
Phase A：小程序前端先行（Now）
   ├─ 5 个页面全部实现（首页 / 新建 / 角色登场 / 对话 / 历史）
   ├─ 调用本地 Mock Server，返回符合接口 ① 出参的假数据
   ├─ Mock 三角色 + 假对话 + 假报告，跑通完整体验
   └─ 真机调试通过 → 上线小样版本

Phase B：后端 Stub 接入（Next）
   ├─ 起一个最小后端服务（FastAPI / Node / Cloud Function 任选）
   ├─ 实现接口 ①「调研输入」+ 接口 ②「对话→报告」+ 报告回写
   ├─ 角色生成、对话编排、报告生成可暂用人工/规则/简单 Prompt
   └─ 前端从 Mock 切到 Stub 后端

Phase C：迁移到完整后端（Later）
   ├─ 真实后端按 docs/specs/API_CONTRACT.md 实现
   ├─ 前端通过 Adapter 层把"小样接口"映射到完整接口组合
   └─ 直接迁移文件 → 前端无需改页面
```

### 9.3 与 API_CONTRACT.md 的术语对照
为后续迁移无缝，本小样的概念命名尽量贴齐完整版：

| 小样字段（v5） | 完整版字段（API_CONTRACT.md） | 备注 |
|---|---|---|
| `sessionId` | `evaluation_id` | 1:1 映射 |
| 调研输入接口 | `POST /products` + `POST /evaluations` + `PUT /evaluations/{id}/personas` + `POST /evaluations/{id}/run` | Adapter 一对多 |
| 角色 `personaId` | `persona_id`（系统库或私有库） | 字段同名 |
| `name` / `occupation` | persona 字段同名 | 直接映射 |
| 对话事件流（接口 ②A） | （完整版无对应 webhook，可由前端轮询 `GET /evaluations/{id}` + `GET /evaluations/{id}/answers` 替代） | Adapter 改 pull |
| 报告回写 | `GET /reports/by-evaluation/{id}` | Adapter 改 pull |

> **关键设计原则**：前端代码只调小样接口；将来迁移时，所有差异由一个 Adapter 层吸收，**前端页面零改动**。

### 9.4 前端架构要点（迁移友好）
- 所有 API 调用走统一 `services/api.ts`（或类似单文件封装）
- 该文件内部判断环境：`mock` / `stub` / `prod`，分别走不同实现
- 业务页面只调 `api.startResearch(...)`、`api.fetchTranscript(...)` 等业务方法，不直接拼 URL
- 迁移到完整版时，**只换 `api.ts` 内部实现**，页面无感

### 9.5 Mock 数据建议
- 3 个 Persona 固定示例：`小芸/白领`、`王姐/全职妈妈`、`朵朵/大学生`
- 9 个话题对应 9×3 条角色回应（thinking + speech），可手写或用线下 Prompt 跑一次保存
- 1 份示例报告，6 个 section
- 文件位置建议：`miniprogram/mock/persona-fixtures.json`

## 10. 阶段拆分（旧 § 9，整合到上节后保留为大节奏视角）

### Phase 1：设计稿（当前）
**目标**：可视化产品形态。
**交付**：
- 本计划书（v3）
- 4 张关键页面设计稿
- 1 段对话+报告浮现的交互动图（可选）

**评审节点**：用户对设计稿满意 → 进入 Phase 2

### Phase 2：微信小程序实现
- 前端：微信小程序原生 / Taro / uni-app（待选）
- 后端：图文理解 + 多角色 prompt 生成 + 多角色对话编排 + 话题循环驱动 + 报告生成
